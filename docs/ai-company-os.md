# AI COMPANY OS ― 設計（フェーズ0）

2026-11-15。Sora が貼った「AI COMPANY OS」の指示書をもとに、今の環境で本当に動く形に落とした設計。
指示書どおり、コードを書く前に「環境の調査・構成・データ・承認・ロードマップ・リスク」をまとめる。

## 1. 今の環境（調べた結果）

| もの | 状態 | 使い道 |
|---|---|---|
| Claude Code（クラウドのセッション） | 使える | AI社員の頭脳。1回の実行＝1人の社員の1仕事 |
| スケジュールタスク（定期実行） | 使える。最短1時間ごと | 「毎週の競合調査」「毎朝の秘書レポート」など |
| Gmail・Google カレンダー・ドライブ・スプレッドシート・Notion のコネクタ | つながっている（ときどき切れる） | 秘書・記録・データベース |
| Google スプレッドシート＋Apps Script | すでに使っている（案件一覧・お店マップ） | 会社のデータベースと、承認ボタンの受け口 |
| Notion Memory | すでに使っている | 長期記憶（Owner／Company／Project） |
| dispatch-viewer（rawcdn で開ける静的ページ） | すでに使っている | ダッシュボード |
| お金 | **使わない**（Sora の方針：1円も払いたくない） | ― |

## 2. 指示書どおりの構成にしない理由

指示書の候補（Next.js・FastAPI・PostgreSQL・pgvector・Redis・Docker・Claude Agent SDK）は、
**サーバーを借りる月額料金**と、**Claude API の従量料金**がかかる。AI社員が自動で動くほどお金が増える。
「お金を使わない」「iPad で使う」「学校で github.io が開けない」に合わない。

→ **同じことを、今あるもので組む**（追加料金0円）。あとでお金をかけられるようになったら、
データベースだけ PostgreSQL に移せるように、表の形はそのまま移せる作りにしておく。

## 3. 構成

```
Sora（経営者）
  │ 指示（チャット） / 承認（ダッシュボードのボタン）
  ▼
CEO（Claude Code のこのセッション）……指示を分けて、部署に割り当てる
  │
  ├─ 定期実行（スケジュールタスク）
  │    秘書：毎朝 7:30 ……メール・予定・期限を読んで「今日のやること」
  │    Research：毎週月曜 ……CrowdWorks・Fiverr・ウィンザーのライバル調査
  │    Marketing：毎週水曜 ……SNS の投稿案（下書きまで）
  │    Finance：毎月1日 ……実際の入金・出金だけで収支（架空の数字は入れない）
  │
  └─ 頼まれたときだけ
       Product / Sales / Creative / Operations
  ▼
Quality Control ……すべての成果物を、出す前に確認（同じ実行の最後に必ず通す）
  ▼
データベース（Google スプレッドシート「AI Company」）
  ▼
ダッシュボード（dispatch-viewer の company.html）……シートを読んで表示、承認ボタンは Apps Script へ
```

AI社員は常に起動しない。**呼ばれたとき・決まった時間だけ**動く（指示書の「必要なときだけ起動」）。

## 4. データベース（スプレッドシートのタブ）

| タブ | 列 |
|---|---|
| Tasks | id・タイトル・部署・状態（待ち/実行中/確認中/完了/失敗）・依存するタスク・成果物リンク・作成日・更新日・エラー |
| Approvals | id・タスクid・操作の種類（メール送信/SNS投稿/購入…）・内容・内容のハッシュ・期限・状態（待ち/承認/却下/期限切れ/実行済み）・承認日時 |
| Reports | 日付・部署・タイトル・要約・出典・確認済みか推測か |
| Activity | 日時・誰が・何をした・結果 |
| Schedules | 自動化の名前・いつ・部署・オン/オフ（ダッシュボードから変えられる） |
| Money | 日付・入金/出金・金額・何の・証拠（スクショやメール） ※実データだけ |

長期記憶は Notion Memory（Owner／Company／Project）。出典・日付・「確認済み／推測」を必ず書く。

## 5. 承認のしくみ（いちばん大事）

- AI社員は **外に出ることを自分でしない**：メール送信・SNS投稿・購入・支払い・広告・予約・データ削除。
  できるのは「下書き」と「Approvals に1行足す」まで。
- Sora がダッシュボードで「承認」を押す → Apps Script が状態を「承認」にする。
- 実行するのは基本 **Sora 本人**（コピペで送る・投稿ボタンを押す）。今までのルール「自動送信しない」と同じ。
- 内容のハッシュを保存して、承認後に中身が変わっていたら実行しない。期限（48時間）を過ぎたら無効。1回実行したら「実行済み」で2回目はできない。
- 正直な限界：サーバーがないので「サーバー側で禁止」は完全にはできない。Gmail のコネクタには送信の機能もあるので、
  **各部署の指示に「送信・投稿は禁止」と書き、スケジュールタスクに付けるコネクタも必要なものだけにする**ことで防ぐ。

## 6. ロードマップ

| フェーズ | 中身 | 完了の条件 |
|---|---|---|
| 1 | シート「AI Company」を作る・ダッシュボード company.html（タスク・承認・レポート・活動）・承認ボタン | シートに書いた行がダッシュボードに出て、承認ボタンで状態が変わる |
| 2 | 秘書：毎朝のレポート（メール要約・今日の予定・期限・返信の下書き） | 3日連続で届き、Sora が使えると言う |
| 3 | Research（毎週）・Marketing（毎週）＋Quality Control | 1回分のレポートが出典つきで Reports に入る |
| 4 | CEO：1つの指示からタスクを分けて、部署を順番に動かす | 「〜を調べて投稿案まで作って」で Research→Marketing→Creative→QC→報告が通る |
| 5 | Finance（実データだけ）・Analytics の画面 | 実際の入金が入った月に、収支が正しく出る |

## 7. リスク

- コネクタがときどき切れる → 失敗したら Activity に記録して、次の回でやり直す。ダッシュボードに「エラー」と出す。
- 使える量の上限（サブスクの範囲） → 定期実行は少なめ（週に数回）から始める。
- 未成年 → お金・契約・外部への送信は全部 Sora と親の確認が必要（今と同じ）。
- 架空の数字 → Finance と Analytics は、証拠がある数字だけを出す。データがない所は「まだデータなし」と表示する。
